# 订单幂等「是否迁移到 DB / 原子 CAS」评估记录

层级：**历史决策层**（讲当初怎么考察、为什么这样权衡）。本文件不据它改新代码；
行为是否仍生效以 `src/host/order-wal.ts`、`src/host/resume-order.ts` 与 `src/` 最终裁决。

## 触探事实还原

评估前对现有实现的触探结论（只记稳定事实，不记行数/时序）：

- 幂等载体：`attemptId` 内存去重 + `ResumeOrderBook` 按源会话尾串行 + `complete` 终态不可覆盖。
- 持久化：`FileResumeOrderWal` 以 append-only JSONL（`%TEMP%\dsh-session-resume\orders.jsonl`，进程内承诺链串行队列）。
  进程内追加不会交错半行；跨进程追加无锁，「最新行胜出」，不保证强一致。
- 崩溃恢复：启动 `load()` 重建终态/planned，`completeResume` 跨重启幂等；WAL 超 1024 时 `rewrite`（临时文件+rename 整写）。
- 缓存根的默认值对所有 Host 进程共享（同机 `%TEMP%`）。

## 评估关键点

现实的并发模型是：attemptId 由**客户端**生成、绑定到**单个 Host**、与单个源会话绑定。
两个 Host 进程对**同一 attemptId** 的竞写，只在「同一客户端路由到两个 Host，且两 Host 共享同一缓存根」时成立——
那不是 DSH 当前的会话/宿部署模型。

## 候选方案与取舍

在插件约束内（typert remote、不自建 HTTP、本地单机、可分发、数据量小）比较：

| 方案 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| T-none（保留 JSONL） | 维持现状，边界已在文档标注 | 零改动、行为不变 | 跨进程无强一致（未触发） |
| T2（文件锁/单写者租约） | 给 append/rewrite 套进程级排他锁 | 封掉共享缓存根窗口，无存储依赖 | 十几行、仍非事务模型 |
| T1（`node:sqlite`/SQLite） | 唯一约束 + UPSERT 原子幂等 | 存储层原子幂等、跨进程一致 | 引入事务存储、迁移面与测试面 |
| T3（外部 KV/Redis/etcd） | 依赖外部服务 | —— | 为单机小状态引入部署依赖，否决 |

## 结论

「订单幂等」本身已是现代化最佳实践（幂等键入**持久存储**、终态不可变、WAL 跨重启恢复、有界重试——均与 AGENTS 红线一致）。

但「迁移到 DB / 原子 CAS」面向的是一个**未触发**的理论边界。按本项目档位纪律（改动小、收益硬、可分发性），

- 默认：**保留 T1 之上的现状（JSONL WAL）**，它在真实单 Host、进程内部署下已正确，跨进程边界如实标注。
- 若在意「白纸黑字的不变量尽早兑现」：**T2（文件锁/单写者租约）**是无存储依赖、行为不变的一步收口。
- **T1（SQLite）仅当**「同一缓存根被多 Host 进程并行续跑、需强一致」成为可复现需求时才立项；届时优先 `node:sqlite`（Node≥22 内置、零原生依赖）而非外部 KV。

> 决策留存：本次不迁移。T1/T2 均为候选，未上排期。此处的「触探+评估」不会改 `src/`。
