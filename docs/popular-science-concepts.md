# 从 DSH 插件聊到 RPC 与分布式：一趟通俗的概念之旅

本文档是**一次探讨的记录**：以 DSH 插件的实际拓扑为起点，层层展开到"为什么叫 host / client"、
"typert 是什么、属于哪类 RPC"、"tRPC / gRPC / Connect 怎么定位"，最后澄清一组最容易被混用的词
——"分布式 / 微服务 / 前后端 / 依赖栈 / 供需栈"，并辨析"相对/绝对"与"依赖/供需"这两个维度。

它定位为**科普笔记**（教学层，随认知理解而更新），**不是**本仓库的"当前为真"技术规范。技术细节
以 `docs/session-resume-architecture.md` 与 `src/` 为准；本文只讲"这些概念是啥、为什么这么叫、
彼此什么关系"。

> 约定：本文无 emoji；所有术语在给出中文说法时尽量并列英文原词，方便你对应官方文档。

---

## 一、起点：DSH 插件是"一个插件，两半区"

我们从一个具体的 DSH 插件出发：`@dsh-external/dsh-session-resume`（一键续跑插件）。它的目标是把
"旧会话 -> 开新会话并续跑"从手工流程压成一次点击。

这个插件的代码分成三层：

- **Host 半区**（`src/index.ts` + `src/host/`）：服务端进程里那份。`SessionResumeService` 是个
  typert Remote 服务，暴露 9 个端点；它能碰文件、会话日志、工作区、写 WAL 与审计。
- **Client 半区**（`src/client/`）：浏览器 GUI 里那份。注册"自动续跑"按钮与输入框 Dock；只做 UI
  与交互，通过 `ctx.remote.sessionResume.*` 去调 Host。
- **共享层**（`src/shared/`）：两边都能 import 的纯逻辑（路径/URI/续跑文本），无副作用。

源码注释里写得直白：`src/index.ts` 首行是"host half"，`src/client/index.ts` 首行是"client half"。
所以准确说，这是**同一个 npm 包，按 DSH 的 host/client 双运行时拆成两份代码**，各自在对应进程加载，
运行时经 typert remote 跨边界通信。这就是 DSH 面向 Web 的插件标准形态：**一个插件 = Host 半区 + Client
半区 + 共享层**。

## 二、为什么叫 host？为什么叫 client？（词义训诂）

很多人被"宿主"这个词带偏，因为中文"宿主"恰好是"寄居的巢穴/寄主"的意思。但 DSH 用的 **host** 是
英文原意。

### host = 主人 / 东道主 / 持有者

- 拉丁词根 `hospes`（主人 vs 客人）。同根：hospital（医院）、hotel（旅馆）。
- 核心是"**持有资源、迎接/招待**"。DSH Host 正是**持有资源的那一方**：文件、会话日志、工作区、
  Agent、磁盘、运行环境都在它手里。别的代码要么"住在它里面（作为插件加载）"，要么"来它家借东西
  （跨端调用）"。
- 所以 **host 不是"载体/机器"，也不是"后端服务器"的官方同义词**。它是"**哪一方持有资源与运行环境、
  当东道主**"的那个**角色**。

**client = 客户 / 委托者 / 依附者**

- 拉丁词根 `cliens`（依附于庇护人的弱小者），同根：clinic、clergy。
- 与 host 正好相对：**没有资源的那一方，来"求取"**。DSH 的 client（浏览器 GUI）手里没有
  files/workspace，它要做什么都得"求" host：帮我 `resolvePlan`、帮我物化、帮我开会话。

一句话对偶：**host 因为有资源所以是"主人"，client 因为没有资源所以是"客户"；两者靠 client 到 host
家里"借东西"维持。**

> 这里要敲掉两个常见误解：
> 1. **host 不等于"那台机器"。** host 是实例里的一个**角色（进程/服务端面）**；机器是承载它运行的
>    **载体**。机器"承载" host，不是 host"管"机器。
> 2. **client 不是"被 host 管理"的下级。** 二者是"供给-依赖"关系：host 提供能力，client 调用/依赖。
>    谁都不是谁的上司。

## 三、机器 / 实例 / 角色：三个不能混的尺度

探讨中反复打架的根源，是大家把三个词当成一个词：

| 尺度 | 是什么 | 举例 |
| --- | --- | --- |
| 机器（machine） | 实实在在的硬件盒子 | 跑 DSH 服务端的那台 Windows 机 |
| 实例（instance / deployment） | 被装配起来、正运行的那整套 | 这一个 DSH 实例（Host 面 + GUI 面 + 环境） |
| 角色 / 面（role / face） | 实例里各司其职的那几个面 | Host 面（服务端）、Client 面（浏览器 GUI） |

"承载"是说：**机器提供 CPU/内存/OS/磁盘，host 进程跑在它上面**。这是**运行场**而非**权责**；
没有一个叫"管理"的维度在其中。别再把"谁跑在哪台机器、谁承载谁"脑补成"谁是上级"。

## 四、typert 是什么：DSH 实例内跨两端的 typed-remote

**typert 是 DSH 官方原生提供的"宿主与客户端两端之间"的类型化远程调用（typed-remote）协议。**

- **两端**：Host（后端服务端面）与 Client（浏览器 GUI），属于**同一个 DSH 实例**。
- **实例内**：指"同一个 DSH 部署拓扑内"，**不**等于"必须同一台机器/同一个进程"——浏览器可能在本机
  也可能远程访问 host 的服务。真正的边是"**同一个实例的两面**"，而非跨两个 DSH 系统或微服务集群。
- **typed-remote**：核心是"**type（类型）+ remote（远程）**"。Client 调 `ctx.remote.sessionResume.resolvePlan(...)` 感觉像调用本地函数，其实把请求发到 Host 的 `SessionResumeService` 执行；而两端
  用什么参数、返回什么，在**构建期由契约生成**、到编译期就能堵住错误。

### typert 是怎么把"类型"落地的？——一条从契约到运行时的真实链路

拿这个插件举例：

1. **写契约**：在 `src/shared/plan.ts` 定义两端共用的 wire 类型（如 `ResumePlan`）；在
   `SessionResumeService` 上用 `@Remote('resolvePlan')` 标记要暴露的方法；`src/typert-meta.d.ts`
   声明协议面。
2. **生成（build 时）**：`dsh-typert-generator` 读你的 TS 类型树，自动生成 `lib/typert.host.*` 与
   `lib/typert.remote-client.*`。里面会看到 `TypertRemoteMap` 里的一条条强类型签名，例如
   `'sessionResume/resolvePlan': (sessionId, attemptId, snapshotId) => Promise<RemoteResult<ResumePlan>>`。
3. **运行时接线**：Host 侧 gateway/registry 挂 `sessionResume/*` 指向 Service；Client 侧
   `remote.$mount(TYPERT_REMOTE)` 挂命名空间，然后 `ctx.remote.sessionResume.*` 就能直接调了。参数/返回
   经 codec/schema 校验。

这即是"类型驱动的 RPC"：**契约先行 + 代码生成**，而不是运行时 reflection 去猜类型。

## 五、RPC 是什么？typert 属于哪一类

**RPC（Remote Procedure Call，远程过程调用）** 是：把一段"不在调用者当场"执行的代码，当成本地函数
来调用的方法。注意它的关键字是**"调用边界"**，而不是"跨网络"：

| 边界在哪 | 是不是分布式 |
| --- | --- |
| 跨机器 / 跨网络 | 分布式 |
| 跨本机进程 | 本地进程间，不一定分布式 |
| 同进程内的组件边界 | 进程内，不算分布式 |

所以 **RPC 不等于"分布式通信"**——分布式只是 RPC"跨机器"那一档场景。RPC 可以在本机、甚至同进程里
照样成立。

而 typert 属于 RPC 家族里现代的一支：**用 TS 类型当契约、由 generator 生成两端（codegen）的类型安全
RPC**。它更接近 gRPC/Thrift 的"契约驱动 + 生成 stub/skeleton"思路，只是它的契约就是 TypeScript
类型、只生成 TS，并且只在 DSH 一个实例内跑。

## 六、排排坐：tRPC / gRPC / Connect / typert

排除绝对"最强"，只按"你要哪条轴"选型：

| 轴 | tRPC | gRPC | Connect | typert |
| --- | --- | --- | --- | --- |
| 契约来源 | 类型继承（无契约） | Protobuf IDL | Protobuf IDL | TS 类型契约 |
| 代码生成 | 有（类型推导） | 生成 stub/skeleton（多语言） | 生成（多语言 + TS） | 生成（TS 双端） |
| 跨语言 | 无 | 强（数十语言） | 强 | 无（仅 TS） |
| 传输/序列化 | HTTP+JSON | HTTP/2 + 二进制 | gRPC/gRPC-Web/HTTP1 | typert 帧（结构化，非二进制） |
| 流式 | 支持订阅实时 | 双向流 | 双向流 | 请求/响应为主 |
| 类型 DX | 极强 | 中上 | 强 | 强 |
| 跨语言的部署面 | 单一栈 | 微服务/跨机 | 微服务+Web | DSH 实例内 |

**定位一句话**：

- **tRPC** —— 纯 TS 全栈，类型体验极限，但无跨语言、无架构红利；"类型爽"王。
- **gRPC** —— 工业级/分布式/跨语言底座之标准，"性能+生态"王。
- **Connect** —— gRPC 的现代化 TS/HTTP 通吃版，跨语言与 TS DX 兼备。
- **typert** —— DSH 这一个封闭运行时里，为"同实例两端、都要 TS、要契约生成"量身的最贴合选择，
  不求当王。

**没有"最强"，只有"谁最贴合你的约束"。** tRPC 并不比 gRPC"强"，只是在"纯 TS 类型体验"这一根轴上是
顶流。

## 七、分布式、微服务、前后端：三个词各自看什么

这三个词中文常被混用，但它们的"轴"不同：

| 词 | 定义看的是什么 | 关键判断 |
| --- | --- | --- |
| 分布式系统 | **物理部署**：组件分布在"多个联网节点"上，消息协同 | 按教科书定义**强调跨节点（跨机）** |
| 微服务 | **架构形态**：后端按业务能力拆成自治、独立部署的小服务 | **不强制跨机**，可单机多进程 |
| 前后端 | **结构形态**：一个（或多个）前端 +（一个或多个）后端 | 即 client-server，不是微服务 |

几个容易被绕的结论串起来：

- **微服务 ⊂ 分布式**只是"只有当它真的跨节点"。**单机 docker 装着几个互 Call RPC 的服务** = "单机
  上的分布式**架构**"，但**不是"分布式部署"**——部署仍是单个物理节点，无冗余/扩容。所以，在**架构（逻辑）
  上算分布式，在部署（物理）上不算。
- **前后端分端** = client-server 架构，**不是微服务**（它不把后端拆成多个自治服务），更不能叫
  "分布式系统"（除非跨机）。
- **分布式一定跨机（按教科书定义）？** 严格定义：是，跨多个联网节点。单机多进程通常叫"多进程"。
- **微服务一定跨机？** 不是。按架构定义可单机部署；生产通常跨机去吃"独立扩展"的红利，但"跨机"不是
  判据。

一句话：**"分布式"看物理部署、'微服务'看架构拆分、'前后端'看结构形态**——三个不同维度，不能互套。

## 八、关系词：别再问"谁管理谁"

技术关系里，真正常用的是**承载 / 依赖 / 供给 / 调用**，而不是"管理 / 上下级"。

- **机器 ↔ host**：运行 / 承载（machine 提供环境，host 跑其上，**单向**）。
- **host ↔ client**：供给 / 依赖（host 给能力，调用/依赖**单向**）。
- **host ↔ 资源**：持有 / 治理。

再深一层，**"调用"与"依赖"要分清**：

| 对子 | 谁依赖谁 | 谁发请求 | 有没有"反向主动" |
| --- | --- | --- | --- |
| 前端 ↔ 后端 | 前端依赖后端 | 前端调后端 | 推送/WS/SSE 时才反向 |
| 后端 ↔ OS | 后端依赖 OS | 后端调 OS（syscall） | 中断/信号时 OS 才插进来 |

所以"双向调用"其实要打折：基础是"**单向发起 + 反向返回**"；只有加了推送/中断这类反向机制才成为
真正的"双向可发起"。但**依赖是单向的**（前端依赖后端、后端依赖 OS，反方向都不依赖）。

这一串可以总结成一句话钩子：

> **依赖与请求都同向（上层求、下层供），串成一条单向供需链；"谁依赖谁"= 结构必要性（单向），
> "谁求谁、谁供谁"= 交易流动（双向）。**

### 依赖栈 vs 供需栈 是不是一个意思？

**在同一根柱子、两个视角**，但不一样：

- **依赖栈** = 谁离不开谁（结构必要性，**单向**）。
- **供需栈** = 谁供、谁求（流动与交易，**双向**：需朝下、供朝上）。

所以，"依赖栈"与"供需栈"不是"一个意思"；一个讲结构（静态必要），一个讲流动（动态交换）。

### host 的相对称谓 vs 绝对身份（两个不同维度）

探讨到"host 是前端的 host"时，又引出一对维度——**相对/绝对** 与 **依赖/供需**。它们**不是同一根轴**，却在 host 上恰好交叠：

- **相对 / 绝对**：问的是"这个叫法是不是依赖另一个词才成立"。host 的**称谓**（"client 的 host / 主人 / 供方"）是**相对** client 的；而 host**身份**（"持资源、跑服务端"）是**绝对**的，即使没有 client 连上来也照样成立。
- **依赖 / 供需**：问的是"单向结构必要，还是双向流动交换"。依赖栈 = 谁依赖谁（**单向**）；供需栈 = 谁求谁供（**双向**：需向下、供向上）。

它们交叠在一个点上：**供给/供需关系本身是成对的、相对的**（有"求"才有资格"供"）；而 host"持资源、跑后端"的**身份却是独立、绝对**的。用 2x2 看：

| 维度 | 相对（关系/称谓） | 绝对（事实/身份） |
| --- | --- | --- |
| 单向（结构/依赖） | 依赖关系成对（client 依赖 host） | 依赖所依托的载体独立存在（后端常驻） |
| 双向（流动/供需） | 供需关系相对（有求才有供） | host 持资源后端的事实不随关系变 |

一句话：**host 相对 client 是"供方/主人"（归属供需的相对层）；同时 host"持资源后端"是绝对身份（归属不变的结构层）——两个维度在一个点上交叠，但不是同一个轴。**

### "业务 / 技术 / 依赖 / 供需"四个词，不是四根平级柱子

有人会把这四个词当成四根并列的"栈"去问它们的先后。但它们其实是**两套不同轴**，不能捏成一条单一顺序：

- **业务栈 → 技术栈**：一根轴，问"目的 → 手段"（为什么做 → 怎么做）。**业务先行、技术跟随**。
- **依赖栈 ↔ 供需栈**：另一根轴，问"同一根柱子的两个视角"（单向结构 → 双向流动）。**不是两层的先后**，
  而是并存的两种看法。

而且"供需"在**多参与方系统**里才长成"栈"（多个供方/求方互相流动）；在**单 client ↔ 单 host** 的插件里
只有**一条供需边**，没有能称"栈"的层级。所以描述这样的单体插件时，**边界应该写成那根真实的依赖链
（官方 API → host → shared → client），而不是套四栈**——套上去是在描述不存在的东西（过度建模）。

## 九、收缩成一张图

把整条线压成一张图：

```text
机器(承载) → host(持有资源,供能力) → client(依附,求资源)   ← 一个 DSH 实例内
                                           依赖/请求都朝下(单向)
                                           供给/资源朝上(与依赖相反)

前端↔后端, 后端↔OS  => 都是"上层求下层"的供需双向, 依赖单向
tRPC/gRPC/Connect/typert => 都是 RPC(跨边界过程调用)的类型化/契约化,
                            差异只在契约来源、是否跨语言、是否网络。

host 相对 client 是"供方/主人"（相对称谓 → 供需层）
host 自身是"持资源后端"（绝对身份 → 结构层）  // 相对/绝对 与 依赖/供需 两维重叠
```

## 十、这一趟的收获清单（速览）

1. **DSH 插件 = Host 半区 + Client 半区 + 共享层**，跨边界经 typert 调用。
2. **host = 持资源的主人（角色），不是机器；client = 依附的客户**。
3. **机器 / 实例 / 角色** 是三个尺度，不能混。
4. **typert = DSH 实例内两端的类型化远程调用（typed-remote）**，由契约 + 生成器实现。
5. **RPC = 跨调用边界的函数调用**，不等于"分布式通信"。
6. **tRPC / gRPC / Connect / typert** 各有胜负轴，没有"绝对最强"。
7. **分布式看物理部署、微服务看架构拆分、前后端看结构形态**，三个轴。
8. **技术关系多用"承载/依赖/供给/调用"，少用"管理/上下级"**。
9. **依赖单向（结构）、供需双向（流动）、调用单向发起 + 反向返回**。
10. **host 的相对称谓（client 的供方/主人）来自供需的相对层；其绝对身份（持资源后端）来自独立的不变层**——"相对/绝对 × 依赖/供需"是两个不同维度。
